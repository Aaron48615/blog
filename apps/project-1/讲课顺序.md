## 项目整体介绍

### 一句话介绍项目

云枢智慧城市数据平台是一个面向智慧城市数据分析场景的后台管理系统。项目目前已经完成登录注册、验证码、登录态持久化、基础路由鉴权、RBAC 菜单与页面权限、明暗主题、仪表盘概览数据和 AI 流式对话等功能；仪表盘图表区、仪表盘管理、图表管理、地图、3D 场景、用户管理、角色管理和个人中心还在继续开发。

### 面试回答统一结构

公开的前端面试题和面经经常会从“项目难点”继续追问 Axios 封装、JWT、双 token、持久化和权限处理。回答项目题时可以统一使用下面五步：

1. **业务目标**：这个功能解决什么问题。
2. **实现流程**：数据从哪里来，经过哪些模块，最后怎样展示或跳转。
3. **技术选择**：为什么使用当前方案，而不是只报库名。
4. **难点与边界**：哪里容易出错，前端和后端各负责什么。
5. **结果与改进**：现在完成到什么程度，下一步怎么优化。

后面的“面试可直接说”都按这个结构组织。公开题库可参考 [Front End Interview Handbook](https://github.com/yangshun/front-end-interview-handbook)，但具体技术结论仍以源码、规范和官方文档为准。

## 已经完成的项目功能

### 配置 Axios 实例和开发代理

我先用 `axios.create` 创建了独立请求实例，统一设置 `/api` 根路径和 10 秒超时。普通业务接口只写 `/auth/login`、`/cities/overview` 这样的相对地址，避免每个接口重复服务器地址，证据见 `src/utils/request.ts:4`。

Vite 开发服务器再把所有 `/api` 请求代理到后端服务器。从浏览器看来，请求仍然发给当前前端源，因此开发阶段不会直接触发浏览器跨域限制，证据见 `vite.config.ts:47`。

`@` 别名需要同时配置两处：

- `vite.config.ts:56` 负责让 Vite 在运行和构建时找到 `src`。
- `tsconfig.app.json:3` 负责让 TypeScript 和编辑器识别 `@/*`。

> [!warning]
> “Vue 一般用 `.env`，React 一般用代理”不是框架规则。Vue 和 React 都能使用环境变量或开发代理。本项目选择代理，是当前项目的工程方案；而且 Vite 的 `server.proxy` 只负责开发环境，生产环境还需要 Nginx、网关代理或生产 API 地址。

官方参考：[Axios 实例](https://axios-http.com/docs/instance)、[Axios 拦截器](https://axios-http.com/docs/interceptors)、[Vite 开发代理](https://vite.dev/config/server-options.html#server-proxy)。

### 统一处理响应和 500 错误

响应拦截器做了两件事：

1. 正常响应直接返回 `response.data`，页面不需要每次再取一层 `response.data`。
2. HTTP 状态为 5xx，或者 HTTP 为 200 但业务 `code` 为 5xx 时，统一跳到 `/500` 页面。

证据见 `src/utils/request.ts:21` 和 `src/pages/ServerError.tsx:4`。

> [!warning]
> 当前请求拦截器只是原样返回配置，还没有读取 Redux 中的 token，也没有统一写入 `Authorization`。因此“我已经在 Axios 请求拦截器中携带 token”暂时不能当作本项目已实现功能，证据见 `src/utils/request.ts:9`。AI 接口是单独在 Fetch 请求头里携带 token，见 `src/pages/AI.tsx:120`。

### 按业务模块管理 API

登录、验证码、注册接口统一放在 `authService` 对象中，调用形式是 `authService.Login()`、`authService.Captcha()` 和 `authService.Register()`，见 `src/api/auth.ts:4`。

仪表盘城市数据接口统一放在 `citiesService` 对象中，当前包含概览、交通、事件类型、事件列表、设施统计和导出接口，见 `src/api/cities.ts:4`。

这样分层以后，页面只负责交互和状态，URL、请求方法等接口细节集中在 `src/api` 中，后续接口地址变化时更容易维护。

### 登录、注册和表单校验

登录流程可以按下面步骤讲：

1. 页面加载时先请求验证码。
2. 用户填写用户名、密码和验证码，Ant Design Form 先做必填校验。
3. 提交后把 `username`、`password`、`captchaId`、`captchaCode` 发给登录接口。
4. 登录成功后把后端返回的 token 和 user 写入 Redux，再跳到首页。
5. 请求进入异常分支时清空验证码输入框并重新获取验证码。

证据见 `src/pages/Login.tsx:33`。

注册页还实现了邮箱格式校验、密码至少八位且同时包含字母和数字、两次密码一致性校验。注册成功两秒后跳转登录页，组件卸载时会清理定时器，见 `src/pages/Register.tsx:31`、`src/pages/Register.tsx:116`。

> [!note]
> 登录页目前只做必填校验，没有复用注册页的密码复杂度正则。面试时可以说“注册页做复杂度校验，登录页避免重复限制已有账号的密码格式，只校验必填；最终是否合法仍由服务端判断”。

### 验证码显示与刷新

验证码逻辑已经从登录、注册页面抽成了 `useCaptcha` Hook，统一管理验证码 ID、SVG 字符串、加载状态、异常提示和刷新方法，见 `src/hooks/useCaptcha.tsx:5`。

后端返回的是 SVG 字符串，当前页面把它用 `btoa` 编码为 Base64，再拼成 Data URL 交给 `<img>` 展示：

```text
data:image/svg+xml;base64,Base64内容
```

- `btoa`：把符合条件的字符串编码成 Base64。
- `atob`：把 Base64 解码回字符串。

验证码刷新已经完成：首次进入页面会刷新；点击验证码会清空输入并刷新；登录或注册请求进入 `catch` 时也会刷新。证据见 `src/pages/Login.tsx:49`、`src/pages/Login.tsx:66`、`src/pages/Login.tsx:114`。

> [!warning]
> `btoa` 直接处理非 Latin-1 字符可能报错。如果后端 SVG 将来包含中文等 Unicode 文本，需要先做 UTF-8 编码，或者直接使用 SVG Blob URL。

### Canvas 动态登录背景

登录和注册页复用了 `LoginBG` 组件。它根据窗口大小设置画布，随机生成星点，并通过 `requestAnimationFrame` 改变透明度，形成闪烁星空背景，见 `src/components/LoginBG.jsx:3`。

这个功能适合当作一个小亮点：Canvas 更适合大量、频繁重绘的像素动画，背景效果不会生成几百个 DOM 节点。

当前可继续改进：组件卸载时除了取消动画，还应该移除 `resize` 监听；当前动画回调会继续创建下一帧，只取消最开始保存的那一个 ID 还不够完整。

### Redux Toolkit 保存登录信息

登录成功后，`authSlice` 保存 token 和用户对象；退出登录时把它们清空，见 `src/store/slice/authSlice.tsx:3`。

仓库使用 `redux-persist` 包装根 reducer，把 `authSlice` 和 `themeSlice` 持久化到浏览器存储。入口再使用 `PersistGate` 等待状态恢复后渲染路由，因此刷新页面后登录态和主题不会马上丢失，见 `src/store/index.ts:8`、`src/main.tsx:30`。

选择 Redux 的原因不是“所有状态都放 Redux”，而是 token、用户信息和主题会被路由守卫、布局、AI 页面等多个位置使用。输入框、弹窗开关、加载状态等页面内部状态仍然使用 `useState`。

### 路由鉴权与 JWT 过期判断

`UseAuth` 把 `/login`、`/register` 作为白名单，并处理两种情况：

- 已登录且 token 未过期时访问登录页，跳回首页。
- 未登录或 token 已过期时访问受保护页面，跳到登录页。

当前代码会取典型 JWT 的第二段 payload，把 Base64URL 字符替换后解码，再读取 `exp`。当距离过期不足 20 秒时，就按已过期处理，见 `src/hooks/UseAuth.tsx:5`。

> [!warning]
> 这只是前端为了页面体验做的过期预判，不等于安全校验。前端解码 payload 不能证明 token 没被篡改，真正的签名、有效期和权限验证必须由服务端完成。

> [!warning]
> 当前项目没有实现 refresh token，也没有自动换取新 token。“提前 20 秒判过期”只是提前退出登录，不是无感刷新。如果面试官问无感刷新，要明确区分当前实现和后续设计。

### 路由表、嵌套路由与懒加载

所有后台页面都是根布局的子路由，所以页面内容会渲染到 Layout 的 `<Outlet />` 中，见 `src/router/index.tsx:29` 和 `src/layout/Layout.tsx:323`。

菜单的视觉层级不等于 URL 层级。比如“数据管理”只是菜单分组，仪表盘管理的实际 URL 仍是 `/dashboards`，不一定要写成 `/data/dashboards`。只要路由表、菜单 key 和跳转地址保持一致即可。

项目还使用 `React.lazy` 和 `Suspense` 懒加载页面组件。首次访问对应路由时再加载页面模块，可以减少首屏一次性加载内容，见 `src/router/index.tsx:6`。

### 403、404、500 异常页面

- 无权限访问会进入 `/403`，见 `src/pages/Forbidden.tsx:4`。
- 不存在的路由由通配符 `*` 进入 404，见 `src/router/index.tsx:146`。
- 请求拦截器发现服务器 5xx 时进入 `/500`，见 `src/utils/request.ts:28`。

这三个页面都使用 Ant Design `Result`，并提供返回首页按钮。

### RBAC：按角色控制菜单

当前权限方案分为两个层次：

1. `ALL_MENUS` 给一级菜单配置允许显示的角色。
2. `ROLE_INFO` 把角色映射成具体权限标识，例如 `users:view`。

登录后从 Redux 用户信息中取 `roleCode`。布局先按一级菜单的 `roles` 过滤可见菜单，再根据 `hasAuthority` 判断叶子菜单权限，没有权限的叶子菜单会被禁用，见 `src/layout/Layout.tsx:15`、`src/layout/Layout.tsx:100`、`src/hooks/useAuthority.tsx:5`。

面试回答：

> 我先用角色控制菜单分组是否可见，再用权限标识控制具体页面或操作是否可用。`super_admin` 用 `*` 表示拥有全部权限，其他角色只配置自己的权限数组。这样比在页面里到处判断角色名更容易维护，后续也能从前端硬编码权限表升级为后端动态返回权限。

### RBAC：页面路由权限

只隐藏菜单不够，因为用户还可以手动输入 URL。布局中维护了路径到权限标识的映射；路由变化后，根据当前路径得到所需权限，再调用 `hasAuthority`，无权限就跳到 403，见 `src/layout/Layout.tsx:188`。

> [!important]
> 前端 RBAC 只负责界面和路由体验，不能代替后端鉴权。所有增删改查接口仍然必须在服务端根据当前用户验证权限。

当前实现还需要注意：

- 路径权限表现在是手写的，容易和路由表重复，后续可以把路由、菜单和权限元信息合并成一份配置。
- 当前 `/profile` 没写进路径权限映射，因此只受登录鉴权保护，没有再做 `profile:view` 页面校验。
- 目前权限表是前端硬编码，更完整的方案是后端返回角色权限，前端只负责消费。

### 面包屑

布局根据 `location.pathname` 在过滤后的菜单中查找当前项。如果命中二级菜单，就同时返回父菜单和当前菜单；如果命中一级菜单，就只返回当前菜单。结果使用 `useMemo` 计算，再交给 Ant Design `Breadcrumb` 展示，见 `src/layout/Layout.tsx:156`。

### 刷新后自动展开二级菜单

菜单使用受控的 `selectedKeys` 和 `openKeys`：

- `selectedKeys` 直接跟随 `location.pathname`，保证当前页面高亮。
- 首次进入布局时，根据当前路径查找父菜单，把父菜单 key 写入 `openKeys`。
- 用户之后手动展开或收起时，由 `onOpenChange` 更新 `openKeys`。

证据见 `src/layout/Layout.tsx:144`、`src/layout/Layout.tsx:178`、`src/layout/Layout.tsx:217`。

当前没有让初始化 effect 持续监听 `location.pathname`，是为了避免用户手动打开多个菜单后，每次切换子页面又被初始化逻辑强制覆盖。

### 明暗主题切换

主题状态保存在 `themeSlice.mode` 中。入口组件根据 mode 切换 Ant Design 的 `defaultAlgorithm` 和 `darkAlgorithm`；布局中的 Switch 派发修改主题的 action，见 `src/store/slice/themeSlice.tsx:3`、`src/main.tsx:13`、`src/layout/Layout.tsx:174`。

因为主题切片也经过 `redux-persist`，刷新后仍会恢复上一次选择。

### 仪表盘首页：当前已完成部分

首页当前已经完成：

- 显示当前日期。
- 并行请求城市概览、交通排行、事件类型、设施统计和事件列表。
- 把概览数据转换为八个 `Statistic` 指标卡。
- 页面加载时请求一次数据。
- 每五分钟重新请求，并在组件卸载时清除定时器。

证据见 `src/pages/Dashboard.tsx:19`、`src/pages/Dashboard.tsx:74`、`src/pages/Dashboard.tsx:94`。

使用 `Promise.all` 的原因是这五个接口互相没有依赖，可以同时发出，整体等待时间更接近最慢的那个接口，而不是五个接口耗时相加。

当前不足：

- `Promise.all` 中任意一个请求失败，整组都会进入失败分支，页面拿不到其他成功结果。后续可根据页面容错要求改成独立请求或 `Promise.allSettled`。
- 交通、事件、设施数据虽然已经请求，但还没有渲染成 ECharts 和表格。
- “导出城市”“导出事件”“管理仪表盘”“刷新”按钮现在没有绑定点击事件。
- 还缺少 loading、空数据和局部错误状态。

### AI 助手与流式响应

AI 页面已经实现需求图中的主要交互：

- AI 消息在左，用户消息在右。
- 输入后立即插入用户消息和一个空的 AI 消息占位。
- 请求过程中显示 Spin，并随着流式事件不断追加文字。
- 新消息出现后自动滚动到底部。
- 支持把 `**内容**` 转成粗体显示。
- 配置弹窗可填写 API Key、Base URL 和模型名，保存后按钮显示“已配置”。

证据见 `src/pages/AI.tsx:9`、`src/pages/AI.tsx:78`、`src/pages/AI.tsx:167`。

这个接口没有走普通 Axios 实例，而是使用 Fetch：

1. 通过 POST 把历史消息发到 `/api/ai/chat`。
2. 用 `response.body.getReader()` 读取字节流。
3. 用 `TextDecoder` 把字节增量解码成字符串。
4. 用换行切分事件，保留不完整的最后一段到下一轮拼接。
5. 遇到 `data: ` 开头的行就解析 JSON，再由异步生成器 `yield` 给页面。

证据见 `src/pages/AI.tsx:120`。这属于 SSE 风格的流式协议，但不是浏览器原生 `EventSource`，因为当前需要 POST、请求体和自定义请求头。

API 配置保存在浏览器 `localStorage`，见 `src/pages/AI.tsx:20`。

> [!warning]
> `localStorage` 中的 token 和 AI Key 都可能在 XSS 发生时被页面脚本读取。个人学习项目可以说明这是当前实现，但生产项目应结合威胁模型考虑 HttpOnly Cookie、后端代管密钥、CSP 和输入输出安全处理。Vite 中所有 `VITE_` 前缀变量也会进入客户端产物，不能当服务端秘密保存。

## 项目亮点、难点和可改进点

### 面试官问：这个项目有哪些亮点

我会选三个有源码支撑的点回答：

1. **权限不是只隐藏菜单**：我同时做了菜单层和路由层校验，避免用户直接输入 URL 访问页面，并预留了按钮级权限标识。
2. **AI 回答是流式展示**：我用 Fetch、ReadableStream、TextDecoder 和异步生成器处理分块响应，让页面边接收边渲染。
3. **登录和主题状态能跨刷新恢复**：我用 Redux Toolkit 管理跨页面状态，再用 redux-persist 恢复登录态和主题。

如果还要补充，可以讲验证码 Hook 复用、路由懒加载、仪表盘并行请求和 Canvas 动画背景。

### 面试官问：最难的功能是什么

可以讲 AI 流式响应：

> 我觉得目前最难的是 AI 流式消息。普通请求等完整 JSON 返回即可，但流式响应一次读取到的 chunk 不一定刚好是一条完整事件。我需要先用 TextDecoder 增量解码，再用缓冲区保留最后一段不完整文本，等下一块数据来了继续拼接。页面更新时也不能直接修改原数组，而是根据 AI 消息 ID 找到占位消息，复制后追加内容。这个功能让我更清楚地理解了网络分块和 React 不可变更新。

也可以讲 RBAC：

> 权限难点不是写一个角色判断，而是让菜单展示、页面访问和按钮操作使用同一套权限语义。当前版本已经实现角色菜单、权限 Hook 和页面守卫；我下一步会把分散配置合并，并把前端硬编码权限升级为后端动态权限。

### 面试官问：登录鉴权是怎么做的

> 用户提交用户名、密码和验证码后，服务端校验身份并返回 token 和用户信息。我把它们存进 Redux，并用 redux-persist 在刷新后恢复。进入页面前，`UseAuth` 会检查 token 是否存在，并解码 JWT 的 `exp` 做前端过期预判；没有 token 或已经过期就跳到登录页。前端这个判断只负责页面体验，受保护接口仍然必须由后端验签和鉴权。当前普通 Axios 拦截器还没有统一带 token，无感刷新也没有完成，这两项是我接下来要补的。

如果后续补全请求鉴权，请求拦截器再统一加入后端约定的 `Authorization`，响应拦截器集中处理 401、清理失效登录态或进入 refresh token 流程。

### 面试官问：项目中做过哪些性能优化

只讲已经做过、而且能解释原因的：

- 页面组件通过 `React.lazy` 做路由级懒加载。
- 仪表盘互不依赖的五个接口使用 `Promise.all` 并行请求。
- 面包屑和权限相关派生数据使用 `useMemo`，权限判断函数使用 `useCallback` 保持引用稳定。
- 定时器在组件卸载时清理，避免重复刷新和内存泄漏。
- Canvas 动画使用 `requestAnimationFrame`，让绘制节奏跟随浏览器刷新。

不要把 `useMemo`、`useCallback` 说成“用了就一定更快”。它们本身也有维护成本，主要在计算明显、引用稳定会影响子组件或 effect 依赖时使用。

- 没有实现 refresh token 和真正的无感刷新。

## 面试题：三个项目的网络请求封装有什么区别

### 先说结论

这三种写法的区别不是由 Vue 2、Vue 3、React 强制决定的，而是三个项目在根地址、鉴权、方法封装和 API 组织上的工程选择不同。

| 项目 | 根地址方案 | 请求实例 | 方法/API 层 | 鉴权与响应处理 |
| --- | --- | --- | --- | --- |
| Vue 2 `bankpro` | `.env` 中的 `VUE_APP_BASE_API`；另有第二个后端根地址 | 有 `request.js` 和 `request2.js` 两个 Axios 实例 | 每个 API 导出命名函数，传 Axios config 对象 | 主实例写 `X-Token`，按业务码 `20000` 判断；第二实例只解包响应 |
| Vue 3 `mobile-shop` | `.env.development` 的 `VITE_APP_URL`，直接请求远程 API | 一个 TypeScript Axios 实例 | 先封装 `getWay/postWay/delWay/putWay`，API 文件再导出一行式业务函数 | 请求头写原始 `Authorization: token`，没有拼 `Bearer`；响应统一返回 `response.data` |
| React `data-pilot` | Axios 用 `/api`，Vite 开发代理转发到后端 | 一个普通 Axios 实例；AI 另用 Fetch | API 按 `authService`、`citiesService` 对象分组 | Axios 目前未带 token，统一解包并处理 5xx；AI Fetch 单独带 Bearer token |

### Vue 2 bankpro

这个项目实际上有两套实例，而且少量旧页面仍然直接使用完整 URL 调 Axios，所以更准确的说法是“主要请求已封装，但历史代码还没有完全统一”：

- `src/utils/request.js` 是模板主请求实例，开发根路径是 `/dev-api`，主要服务于模板/mock 接口。请求拦截器从 store/cookie 工具取 token，写入 `X-Token`；响应按业务码 `20000` 判断，token 非法或过期时提示重新登录。
- `src/utils/request2.js` 连接另一个业务服务器，根路径来自 `VUE_APP_BASE_API_2`，只做响应解包和错误提示。

业务 API 采用命名函数，每个函数传入一个包含 `url`、`method`、`data/params` 的 Axios 配置对象，例如 `src/api/address.js`。

优点是灵活、接近 Axios 原生配置，多后端可以各建实例；缺点是两个实例的鉴权和错误策略不一致，页面维护时需要知道该选哪一个。

### Vue 3 mobile-shop

这个项目用 TypeScript 创建 Axios 实例，根地址来自 `import.meta.env.VITE_APP_URL`。请求拦截器读取 token 并直接放进 `Authorization`，没有添加 `Bearer` 前缀；具体格式以这个项目的后端约定为准。响应拦截器统一返回业务数据。

在实例外又封装了一层 `getWay`、`postWay`、`delWay`、`putWay`。业务 API 因此很短，例如 `loginInfo(data)` 只需要调用 `postWay('/login', data)`。

优点是页面和 API 层写法统一、调用简单；缺点是通用方法参数比较粗，目前大量使用 `any`，遇到上传、下载、特殊 header、取消请求等场景时还要扩展配置入口。

### React data-pilot

这个项目不把后端完整地址暴露给页面，而是让 Axios 统一请求 `/api`，开发服务器代理到后端。业务 API 不是单个命名函数，而是按领域组织成 service 对象。

响应拦截器同时处理 HTTP 5xx 和业务 5xx。AI 聊天因为需要读取流，单独使用 Fetch 和 ReadableStream，没有强行塞进普通 JSON Axios 流程。

当前不足是 Axios 请求拦截器没有携带 token，后续应让它从可访问的认证存储中读取最新 token，并统一处理 401；同时要避免刷新 token 时多个请求并发触发多次刷新。

### 三个项目登录密码处理也不一样

- Vue 3 `mobile-shop` 在登录和注册提交前调用 `encrypt`，把“时间戳 + 明文密码”使用 CryptoJS AES-ECB 加密，再把结果放进请求体，证据见 `mobile-shop/src/views/Login.vue:53`、`mobile-shop/src/utils/cryptojs.ts:10`。
- React `data-pilot` 当前直接把表单密码放进登录请求体，没有额外做应用层 AES，见 `src/pages/Login.tsx:33`。

面试时可以说明项目差异，但不能把前端 AES 说成可以代替 HTTPS。因为加密代码和固定对称密钥都会随前端资源下发，使用者能够看到；真正的传输机密性依赖 HTTPS，服务端还应对密码做安全哈希存储。前端额外加密只有在后端协议明确要求时才按双方约定实现。

### 面试时的完整回答

> 三个项目都是以 Axios 实例为基础，但抽象层次不同。Vue 2 项目更接近 Axios 原生 config，而且因为连接两个后端维护了两个实例；Vue 3 项目在实例外再封装 GET、POST、PUT、DELETE 通用方法，业务 API 最精简，登录提交前还按后端约定做了 AES 处理；React 项目使用 Vite 代理隐藏开发环境后端地址，并按领域把接口放在 service 对象里，同时把普通 JSON 请求和 AI 流式请求分开。我的体会是封装不是层数越多越好，核心是统一根地址、鉴权、错误处理和返回类型，同时保留特殊配置的出口。

## 面试题：SVG 和 Canvas 的区别

### 核心区别

| 对比项 | SVG | Canvas |
| --- | --- | --- |
| 图形模型 | 矢量图形、XML/DOM 元素 | 位图画布、像素绘制 |
| 缩放 | 放大通常不失真 | 画布像素放大可能模糊，需要处理分辨率 |
| 事件 | 图形节点可以单独绑定事件 | 通常要自己根据坐标判断点中了什么 |
| 更新方式 | 修改某个 DOM 图形节点 | 经常需要清空并重新绘制 |
| 大量对象 | DOM 节点很多时开销会增加 | 大量、高频绘制通常更合适 |
| 可访问性 | 文本和节点更容易被搜索、读取 | 画布内容本身不提供等价语义，需要额外处理 |
| 常见场景 | 图标、流程图、需要交互的矢量图 | 游戏、粒子动画、图片处理、高频动态图形 |

### 结合当前项目回答

> SVG 是基于 XML 的矢量图形，每个图形可以成为 DOM 节点，适合需要清晰缩放和单元素交互的内容；Canvas 是一块通过 JavaScript 绘制的位图画布，更适合大量对象和高频重绘。当前项目里，验证码由后端返回 SVG，所以缩放后仍然清晰；登录页星空需要每帧更新大量星点，所以我选择 Canvas。后续 ECharts 也可以根据图表规模选择 Canvas 或 SVG 渲染器。

“SVG 永不失真”可以换成“矢量内容在正常缩放时不会像位图那样像素化”，表达更严谨，因为滤镜、嵌入位图等内容仍可能受影响。

官方参考：[MDN SVG](https://developer.mozilla.org/en-US/docs/Web/SVG)、[MDN Canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Basic_usage)、[Canvas 可访问性与像素缩放](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Drawing_text#accessibility_concerns)。

ECharts 本身同时支持 Canvas 和 SVG renderer，默认使用 Canvas；选择时要按数据量、设备、内存和缩放需求实测。官方参考：[ECharts Canvas 与 SVG](https://echarts.apache.org/handbook/en/best-practices/canvas-vs-svg/)。

## 面试题：HTTP 状态码怎么看

先按第一位分五类：

- `1xx`：信息响应，请求还在继续处理。
- `2xx`：请求成功，如 `200 OK`、`201 Created`、`204 No Content`。
- `3xx`：重定向，如 `301`、`302`、`304 Not Modified`。
- `4xx`：客户端请求存在问题，如 `400`、`401`、`403`、`404`。
- `5xx`：服务端处理失败，如 `500`、`502`、`503`。

常见易错点：

- `401` 更准确地说是“未认证或认证失效”，通常需要登录或更新凭证。
- `403` 是服务端知道你是谁，但你没有访问权限。
- `404` 是资源不存在。
- `500` 是服务端内部错误。
- HTTP `200` 只代表 HTTP 层成功，响应体里的业务 `code` 仍可能表示业务失败。

结合项目回答：

> 我的请求封装会同时看 HTTP 状态和业务状态。HTTP 5xx 会进入 Axios 的错误分支；如果后端虽然返回 HTTP 200，但业务 code 是 5xx，我也会统一跳到 500 页面。登录页面则根据业务 code 判断登录是否成功。

官方参考：[MDN HTTP 状态码](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)。

## 面试题：什么是 JWT

JWT 是一种紧凑、URL 安全的声明传输格式，常用于在客户端和服务端之间传递身份与授权相关信息。

常见的签名 JWT，也就是 JWS Compact 形式，由三段组成，中间用 `.` 分隔：

1. Header：说明 token 类型和签名算法。
2. Payload：保存用户标识、角色、过期时间等 claims。
3. Signature：服务端用密钥对前两部分签名，用于判断内容有没有被篡改。

重要纠错：

- Header 和 Payload 通常只是 Base64URL 编码，不是加密，不能存密码等敏感明文。
- 前端可以解码 payload 看 `exp`，但不能因此相信角色或用户信息。
- 服务端收到受保护请求后必须验证签名、有效期和权限。
- `exp` 是从 Unix Epoch 开始计算的秒数，JavaScript `Date.now()` 是毫秒，所以比较时要统一单位。
- JWT 是一种 token 格式，不等于完整的登录、刷新和注销方案。
- JWT 还可以使用 JWE 加密形式，所以“JWT 永远只有三段”并不严谨；当前项目接触的是常见三段签名 token。

结合项目回答：

> 登录成功后，我把后端返回的 token 和用户信息保存到 Redux，并通过 redux-persist 跨刷新恢复。路由守卫解码 JWT payload 的 `exp` 做前端过期预判，提前 20 秒把它视为过期。但这只是路由体验，服务端接口仍然必须验证签名。当前项目还没有 refresh token，所以我不会把它说成已经实现了无感刷新。

官方参考：[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)。

### 如果继续实现无感刷新

比较完整的设计是：

1. access token 设置较短有效期，refresh token 设置较长有效期。
2. 普通请求收到约定的 401，或者请求前判断 access token 即将过期时，调用刷新接口。
3. 刷新期间使用一个共享 Promise 或请求队列，避免多个并发请求同时刷新。
4. 刷新成功后更新 access token，并重放等待中的请求。
5. 刷新失败时清空登录态并跳转登录页。

是否把 refresh token 放 HttpOnly Cookie，要结合后端架构、CSRF 防护和跨域策略决定。

## 面试题：GET 和 POST 的区别

不要只回答“GET 参数在 URL，POST 参数在 body”，更好的回答要先讲 HTTP 语义。

| 对比项 | GET | POST |
| --- | --- | --- |
| 主要语义 | 获取资源 | 向资源提交数据，常用于创建或触发处理 |
| 安全性语义 | 应该是 safe，不应主动改变服务端业务状态 | 通常会产生状态变化或副作用 |
| 幂等性 | 应该幂等，多次相同请求效果等价 | 默认不保证幂等，重复提交可能创建多份数据 |
| 缓存 | 更适合被浏览器、代理缓存 | 只有满足明确缓存条件时才缓存 |
| 参数位置 | 查询条件通常放 URL query | 数据通常放请求体，格式可为 JSON、表单、文件等 |
| 收藏/分享 | URL 包含查询条件，通常更容易收藏和分享 | 请求体不会自然进入书签 |
| 数据量 | URL 在浏览器、服务器、代理中存在实际长度限制 | 请求体通常可承载更多数据，但服务端仍会限制大小 |

安全性纠错：

- POST 不会天然比 GET 加密；是否加密取决于 HTTPS。
- GET 查询参数更容易出现在地址栏、历史、日志和监控记录中，所以敏感数据不应该放 URL。
- POST 也不能发送明文密码到 HTTP 地址，必须使用 HTTPS。

结合项目举例：

- 获取验证码、城市概览使用 GET，因为它们是读取资源。
- 登录、注册、AI 对话使用 POST，因为需要提交结构化数据，并可能产生服务端状态或处理任务。

官方参考：[MDN HTTP 请求方法](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods)。

## 其他高频项目面试题

### 鉴权和权限控制有什么区别

- 鉴权解决“你是谁、是否已登录”，当前项目用 token 和 `UseAuth` 处理。
- 权限控制解决“你能做什么”，当前项目用 role、权限标识、菜单过滤和页面守卫处理。

回答时把两者分开，不能用“有 token”直接代表“有所有页面权限”。

### 为什么要封装请求

> 我封装请求不是为了少写几行，而是为了集中处理根地址、超时、token、响应解包、业务错误和页面跳转。业务 API 再按模块管理，使页面不依赖具体 URL。特殊请求仍然保留出口，例如 AI 流式接口用 Fetch，文件下载要使用 Blob 配置。

### 为什么开发代理能解决跨域

浏览器同源策略约束的是浏览器发出的跨源请求。页面请求当前开发服务器的 `/api` 时仍然同源，再由 Vite 的 Node 开发服务器把请求转发到后端；服务器到服务器不受浏览器同源策略限制。

代理不是“让两个地址变成真的同源”，而是让浏览器只看见同源入口。生产环境不能依赖 Vite 开发服务器，要由部署层继续代理或让后端正确配置 CORS。

### `useMemo` 和 `useCallback` 有什么区别

- `useMemo` 缓存一次计算得到的值，例如当前面包屑对象、过滤后的菜单。
- `useCallback` 缓存函数引用，例如 `hasAuthority`、`fetchData`。

它们都只是一种性能和引用稳定工具，不保证业务正确，也不是所有函数和计算都应该缓存。依赖项变化时缓存会重新计算。

官方参考：[React useMemo](https://react.dev/reference/react/useMemo)、[React useCallback](https://react.dev/reference/react/useCallback)。

### 为什么使用 `Promise.all`

> 首页的五个数据接口互不依赖，所以我用 `Promise.all` 并行请求，减少总等待时间。它是 fail-fast 的，一个 Promise 拒绝时整体就拒绝。当前首页数据需要整体一致，所以先用了这个方案；如果以后希望某个图表失败但其他图表仍展示，我会改成 `Promise.allSettled` 或每个模块独立管理状态。

### SSE、普通请求和 WebSocket 怎么选

- 普通请求：一次请求对应一次完整响应，适合普通 CRUD。
- SSE：服务端持续向客户端推送文本事件，适合 AI 文本生成、通知、进度；传统 EventSource 主要是服务端到客户端。
- WebSocket：建立全双工长连接，适合双方都需要高频实时通信的聊天、协同和游戏。

当前 AI 使用 POST 加自定义请求头，所以采用 Fetch 读取 SSE 风格流，而不是直接使用 EventSource。

### 前端 RBAC 能保证安全吗

不能。前端 RBAC 可以隐藏菜单、禁用按钮、阻止普通页面跳转，但用户可以修改前端代码或直接调用接口。真正的安全边界必须在后端；后端要从已验证身份中取用户角色，而不是相信前端传来的角色。

### token 为什么需要持久化，有什么风险

持久化是为了刷新后保留登录体验，但浏览器可读存储会受到 XSS 风险影响。生产项目可以考虑：

- access token 只放内存，刷新后通过安全刷新机制恢复。
- refresh token 使用 Secure、HttpOnly、SameSite Cookie。
- 配置 CSP，避免不可信脚本执行。
- 不在 token payload 或前端环境变量中保存秘密。

没有一种存储方案在所有项目中都绝对最好，要同时考虑 XSS、CSRF、跨域和后端能力。

### 如果面试官问项目还没做完怎么办

可以直接说：

> 这个项目目前还在开发，我已经把登录鉴权、权限模型、公共布局、主题、仪表盘数据接入和 AI 流式对话这些基础链路跑通。管理类页面目前只有路由和菜单占位，我已经根据需求图拆出了列表、筛选、分页、弹窗和权限配置等任务。面试里我会重点讲已经完成并能从源码解释的功能，未完成部分只讲设计方案，不把它说成现有成果。

这比回答“项目全部完成了”更经得住追问。

## 后续完成一个页面后要补哪些总结

每完成一个页面，至少补下面六项：

1. 页面解决什么业务问题。
2. 使用了哪些接口，请求参数和返回数据如何转换。
3. 页面状态如何拆分，哪些放本地，哪些放 Redux。
4. 核心交互流程，如筛选、分页、新增、编辑、删除、回显。
5. 权限、loading、空数据、失败、重复提交等边界情况。
6. 一个真实难点、取舍和后续改进点。

这样最后总结项目时，不会只剩“我用了某某组件库”，而是能讲清业务流程、数据流和工程取舍。
