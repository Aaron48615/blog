## 先说最需要修正的几点

1. **不是“Vue 用 `.env`，React 用代理”。** `.env` 和开发代理是构建工具提供的能力，不是 Vue/React 的固定差异。Vue CLI 支持 `.env` 和 `devServer.proxy`；Vite 同样支持 `.env` 和 `server.proxy`，而 Vite 既可以用于 Vue 也可以用于 React。来源：[Vue CLI 环境变量](https://cli.vuejs.org/guide/mode-and-env.html)、[Vue CLI `devServer.proxy`](https://cli.vuejs.org/config/#devserver-proxy)、[Vite 环境变量](https://vite.dev/guide/env-and-mode)、[Vite `server.proxy`](https://vite.dev/config/server-options.html#server-proxy)。
2. **云枢智慧城市数据平台现在还不能说“Axios 拦截器统一携带 token”。** 当前请求拦截器只原样返回 `config`，没有设置 `Authorization`。AI 页面的流式请求是手动添加 `Bearer` 头，不等于 Axios 已全局处理。来源：[云枢智慧城市数据平台 `request.ts`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/utils/request.ts:9)、[云枢智慧城市数据平台 `AI.tsx`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/pages/AI.tsx:120)。
3. **云枢智慧城市数据平台现在不是“无感刷新 token”。** 它只是在 `exp` 前 20 秒把 token 视为过期，然后路由守卫跳回登录页；代码中没有 refresh token 请求、并发队列或失败重放。来源：[云枢智慧城市数据平台 `UseAuth.tsx`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/hooks/UseAuth.tsx:5)。
4. **HTTP 状态码和业务状态码要分开。** `response.status` 是 HTTP 层的状态码，`response.data.code` 是项目接口自定义的业务码。云枢智慧城市数据平台已经分别处理“HTTP 5xx”和“HTTP 200 但业务 code 是 5xx”。来源：[Axios 响应结构](https://axios-http.com/docs/res_schema)、[云枢智慧城市数据平台 `request.ts`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/utils/request.ts:21)。

## 1. 三个项目的网络请求封装

### 先用一个共同模型理解

三个项目虽然写法不同，但都能拆成三层：

1. **请求基础层**：`axios.create()` 配置 `baseURL`、超时、请求/响应拦截器；
2. **API 定义层**：把 URL、method 和参数封装成有业务含义的方法；
3. **页面调用层**：页面只调用 `login()`、`authService.Login()` 等方法，不重复写完整 URL 和公共处理。

Axios 官方说明 `axios.create()` 可以建立预配置实例，`baseURL` 会拼在相对 `url` 前，拦截器可在请求发送前或响应进入业务代码前统一处理。来源：[Axios 实例](https://axios-http.com/docs/instance)、[Axios 请求配置](https://axios-http.com/docs/req_config)、[Axios 拦截器](https://axios-http.com/docs/interceptors)。

### 项目对比

| 项目 | 实际封装方式 | `baseURL` 来源 | API 层风格 | token/响应处理 |
| --- | --- | --- | --- | --- |
| Vue 2 `bankpro` | 主要用 `request({...})` 传递 Axios 配置对象；并且为不同服务维护了 `request.js` 和 `request2.js` 两个实例 | Vue CLI 的 `process.env.VUE_APP_BASE_API` / `_2`；一套走 `/dev-api` mock，一套直连外部服务 | 导出普通函数，函数内写 `{ url, method, data/params }` | 主实例把 token 放到自定义 `X-Token`，并以业务码 `20000` 判定成功；`request2` 只解包 `response.data` |
| Vue 3 `mobile-shop` | 先封装 `getWay/postWay/putWay/delWay`，再让 API 方法调用这些 HTTP 助手函数 | Vite 的 `import.meta.env.VITE_APP_URL`，直连远程 API | 导出箭头函数，如 `confirmInfo(data) => postWay(...)` | 请求拦截器写入 `Authorization: token`，注意当前没有拼 `Bearer `；响应拦截器返回 `response.data` |
| React `data-pilot` | 保留 Axios 实例原生的 `.get/.post`，API 层用 service 对象按领域分组 | Axios `baseURL` 是 `/api`，Vite 开发服务器把 `/api` 代理到后端 | `authService.Login()`、`authService.Captcha()` 这类对象方法，并标注 TS 返回类型 | 目前请求拦截器未加 token；响应拦截器解包 `response.data`，同时区分 HTTP 5xx 和业务 5xx 并跳转 500 页 |

### 面试可直接说

> 我这三个项目都是用 Axios，核心目的一样，就是把基础地址、超时、token 和错误处理从页面里抽出来，但 API 层的组织方式是逐步调整的。Vue 2 项目是把 Axios 配置对象传给 `request()`，而且因为有两个后端地址，使用了两个 Axios 实例。Vue 3 项目在实例外又封装了 `getWay` 和 `postWay` 等方法，API 文件只需要传路径和参数。React 项目直接保留 Axios 的 `get/post` 方法，再用 `authService` 这样的对象按业务域组织 API，并用 TypeScript 标注返回类型。这些是项目结构上的差异，不是 Vue 和 React 对 Axios 有不同限制。

如果面试官追问代理，可以补充：

> 云枢智慧城市数据平台在开发时请求 `/api/auth/login`，浏览器看到的是前端同源地址，Vite dev server 再把 `/api` 开头的请求代理到后端。这个 `server.proxy` 是开发服务器配置；上线后还需要 Nginx/API Gateway 的反向代理，或者用环境变量配置生产 API 地址。

Vite 官方把 `server.proxy` 明确定义为 dev server 的自定义代理规则；匹配到前缀的请求会被代理到 `target`。来源：[Vite `server.proxy`](https://vite.dev/config/server-options.html#server-proxy)。

### 不要超出当前代码来讲

- Vue 2 存在两个实例，少量旧页面还直接调用 Axios 完整 URL，因此更准确的说法是“主要已封装，但历史代码尚未完全统一”。例子：[`LevelList.vue`](/Users/aaron/LoveCoding/Vuecli_10/bankpro/src/views/level/LevelList.vue:25)。
- Vue 3 的 `Authorization` 是原始 token，不能为了显得规范就说它已经使用 `Bearer`。`Bearer <token>` 是一种标准授权方案，但实际格式必须和后端约定一致。来源：[RFC 6750 第 2.1 节](https://datatracker.ietf.org/doc/html/rfc6750#section-2.1)。
- 云枢智慧城市数据平台只能说“留出了请求拦截器”，不能说“已统一注入 token”，除非后续把它实现并验证。

## 3. SVG 和 Canvas 的区别

### 准确对比

| 维度 | SVG | Canvas |
| --- | --- | --- |
| 本质 | 基于 XML/HTML 语法描述二维图形，存在元素树和 DOM | 一块与分辨率相关的 bitmap，通过 2D/WebGL/WebGPU 等 rendering context 绘制 |
| 缩放 | 矢量形状可按几何描述重新渲染，放大通常不会像位图那样出现像素块 | 画布本身是位图，只用 CSS 放大会拉伸现有像素；高 DPI 需同步调整 bitmap 尺寸并重绘 |
| 元素和事件 | 图形对象是 DOM 元素，可用 CSS、DOM API 和元素级事件 | 绘制后只是像素，单个图形不自动成为 DOM 节点，交互需自己做坐标/命中管理或交给图表库 |
| 更新模型 | 修改对应元素后由浏览器重新渲染 | API 命令改变 bitmap；要维护可交互对象，通常要额外保留场景状态并按需重绘 |
| 适用场景 | icon、logo、中小数量图形、需要 DOM/CSS/可访问语义的图形 | 粒子、游戏、图像处理、数据点很多或频繁重绘的可视化 |
| 可访问性 | 可通过 SVG DOM、`title/desc`、ARIA 组织语义 | bitmap 不自动暴露图形语义，需提供等价 fallback 内容和键盘交互映射 |

SVG 2 规范把 SVG 定义为基于 XML 的二维矢量和混合矢量/位图描述语言，并支持 DOM、动画和交互。HTML 规范把 Canvas 定义为“resolution-dependent bitmap canvas”，并明确要求作者提供能表达同等目的的 fallback 内容。来源：[W3C SVG 2](https://www.w3.org/TR/SVG/)、[SVG 介绍与 DOM](https://www.w3.org/TR/SVG/intro.html)、[WHATWG Canvas](https://html.spec.whatwg.org/multipage/canvas.html#the-canvas-element)。

### 和云枢智慧城市数据平台/ECharts 的关系

ECharts 同时支持 Canvas 和 SVG renderer，默认是 Canvas。官方给出的实践是：数据元素很多、大规模折线/散点/热力图通常更倾向 Canvas；在移动低端设备、图表实例很多或强调缩放清晰度时可以评估 SVG，最终要根据数据量和环境做实测。来源：[Apache ECharts：Canvas vs SVG](https://echarts.apache.org/handbook/en/best-practices/canvas-vs-svg/)。

### 面试可直接说

> SVG 是用标签描述图形的矢量图技术，每个图形都能成为 DOM 元素，所以适合需要 CSS、元素事件和无损缩放的场景。Canvas 是由 JavaScript 在一块位图上绘制，单个图形不是 DOM 节点，但在大量对象和频繁重绘的场景中通常更合适。在云枢智慧城市数据平台中我用 ECharts，它默认使用 Canvas，也支持切换 SVG；选择时我会根据数据量、缩放清晰度、内存和交互需求实测，不是简单说哪个一定更好。

`SVG 是永不失真的图标` 建议改成“SVG 中的矢量形状放大时通常不会像位图一样像素化”。SVG 也可以嵌入位图，且最终显示仍会由设备栅格化，“永不失真”过于绝对。

## 4. HTTP 状态码怎么看

### 五大类

HTTP 状态码是 100–599 的三位整数，第一位决定类别：

- `1xx Informational`：已收到请求，过程继续；
- `2xx Successful`：请求已成功收到、理解并接受；
- `3xx Redirection`：需要进一步操作才能完成请求；
- `4xx Client Error`：请求有错或无法完成；
- `5xx Server Error`：服务器未能完成一个表面上有效的请求。

这个分类来自 HTTP 语义规范，应当补上原笔记漏掉的 `1xx`。来源：[RFC 9110 第 15 节](https://httpwg.org/specs/rfc9110.html#status.codes)。

### 前端常遇到的具体码

| 状态码 | 简要含义 | 前端常见处理 |
| --- | --- | --- |
| `200 OK` | 请求成功 | 正常解析响应，还要看业务 code |
| `201 Created` | 已创建新资源 | 新增成功后更新列表/跳详情 |
| `204 No Content` | 成功但无响应内容 | 不应强行解析 JSON |
| `301/308` | 永久重定向 | 多由浏览器/代理处理；308 不改请求方法 |
| `302/307` | 临时重定向 | 307 明确不改请求方法 |
| `304 Not Modified` | 条件请求中资源未修改 | 复用缓存，它不是“发生错误” |
| `400 Bad Request` | 请求语法/参数等导致无法处理 | 检查入参和序列化 |
| `401 Unauthorized` | 没有有效认证凭证 | 登录/token 刷新流程 |
| `403 Forbidden` | 服务器理解请求但拒绝执行 | 进入 403 或隐藏无权操作，不要和 401 混淆 |
| `404 Not Found` | 找不到目标资源 | 空状态或 404 页 |
| `405 Method Not Allowed` | 目标资源存在，但不支持该请求方法 | 检查 API 文档和 method，服务器应返回 `Allow` |
| `409 Conflict` | 与资源当前状态冲突 | 如重复创建/并发更新，展示可操作提示 |
| `422 Unprocessable Content` | 语法正确但内容指令无法处理 | 展示字段级校验错误 |
| `429 Too Many Requests` | 请求频率过高 | 读 `Retry-After`，做限流提示/合理重试 |
| `500 Internal Server Error` | 服务器内部错误 | 统一错误提示/上报，不向用户暴露堆栈 |
| `502 Bad Gateway` | 网关从上游收到无效响应 | 提示服务暂不可用，记录链路信息 |
| `503 Service Unavailable` | 服务临时不可用 | 根据 `Retry-After` 决定是否稍后重试 |
| `504 Gateway Timeout` | 网关等待上游超时 | 超时提示、记录和有条件重试 |

具体状态码的规范语义见 [RFC 9110 第 15.1–15.6 节](https://httpwg.org/specs/rfc9110.html#status.codes)；最新注册表见 [IANA HTTP Status Code Registry](https://www.iana.org/assignments/http-status-codes/http-status-codes.xhtml)。

### 结合云枢智慧城市数据平台的面试说法

> 我先按首位判断 HTTP 状态码的类别：1xx 是信息，2xx 成功，3xx 需要进一步操作，4xx 是客户端请求问题，5xx 是服务端处理失败。实际项目中我还会区分 HTTP 状态码和业务状态码。云枢智慧城市数据平台的 Axios 失败拦截器会从 `error.response.status` 处理真正的 HTTP 5xx，成功拦截器还会检查 `response.data.code`，兼容 HTTP 200 但业务失败的接口约定。

## 5. 什么是 JWT

### 标准定义

JWT（JSON Web Token）是一种紧凑、URL-safe 的 claims 表示格式。Claims 是一组用 JSON 表示的声明，JWT 可作为 JWS 被签名/做 MAC 完整性保护，也可作为 JWE 被加密。来源：[RFC 7519 摘要与第 1 节](https://datatracker.ietf.org/doc/html/rfc7519#section-1)。

常见的“三段 JWT”准确说是 **JWS Compact Serialization**：

1. JOSE Header：例如 token 类型和签名算法；
2. Payload / JWT Claims Set：例如 `sub`、`role`、`iat`、`exp`；
3. Signature/MAC：用来校验前两段是否被篡改。

各部分用 Base64url 编码并以 `.` 分隔。要注意：Base64url 是编码，不是加密；常见的签名 JWT 的 payload 可被解码查看，不应放密码等敏感明文。而 JWE Compact Serialization 不是三段，所以“JWT 永远是头部、载荷、签名三段”并不严谨。来源：[RFC 7519 第 3 节](https://datatracker.ietf.org/doc/html/rfc7519#section-3)、[JWS Compact Serialization](https://datatracker.ietf.org/doc/html/rfc7515#section-3.1)、[JWE Compact Serialization](https://datatracker.ietf.org/doc/html/rfc7516#section-3.1)。

`exp` 是 NumericDate，表示 token 在该时间点及之后不得再被接受；验证方可以为时钟偏差留少量容差。来源：[RFC 7519 `exp`](https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.4)。

### “解码”和“验证”不是一件事

前端把 payload Base64url 解码后读取 `exp`，只能用于改善 UI 体验，不能证明 token 真实有效，因为攻击者也可以伪造 payload。真正的权限保障必须在服务端校验签名/MAC、可接受算法、`exp`、issuer 和 audience 等约束，再对每个受保护接口做授权。JWT 安全最佳实践要求显式限定可用算法、校验密码学操作，并按场景验证 issuer/audience。来源：[RFC 7519 第 7.2 节](https://datatracker.ietf.org/doc/html/rfc7519#section-7.2)、[RFC 8725 第 3 节](https://datatracker.ietf.org/doc/html/rfc8725#section-3)。

### 结合云枢智慧城市数据平台的已实现部分

云枢智慧城市数据平台登录成功后把 `token` 和 `user` 保存到 Redux，再由 `redux-persist` 使他们持久化。路由守卫解码 payload 的 `exp`，在到期前 20 秒开始将它判为过期，无 token 或过期时跳登录页。代码来源：[`Login.tsx`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/pages/Login.tsx:32)、[`authSlice.tsx`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/store/slice/authSlice.tsx:3)、[`store/index.ts`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/store/index.ts:9)、[`UseAuth.tsx`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/hooks/UseAuth.tsx:5)。

> JWT 是一种紧凑的 JSON claims 令牌格式。我这个项目接触的是常见的签名 JWT，它由 Base64url 编码的 header、payload 和 signature 组成。Payload 可以放用户标识、角色和过期时间，但 Base64url 只是编码，不是加密，所以不放密码这类敏感明文。前端会解码 `exp` 来提前调整路由和界面，但解码不等于验签，真正的鉴权和授权必须由服务端验证签名、有效期和权限。目前云枢智慧城市数据平台已完成 token 持久化和前端过期判定，token 全局注入与无感刷新还是待完成项。

## 6. GET 和 POST 的区别

### 要从 HTTP 语义回答，不只说“一个放 URL，一个放 body”

| 维度 | GET | POST |
| --- | --- | --- |
| 规范语义 | 请求传输目标资源当前选定的 representation | 请求资源按自身规则处理请求中携带的内容 |
| 安全方法（safe） | 是：客户端请求的语义是只读 | 否：常用于提交、创建、执行命令等会变更状态的操作 |
| 幂等（idempotent） | 是：多次相同请求的预期服务器效果与一次相同 | 规范不保证：重试可能导致重复下单/重复扣款，需业务幂等键等机制 |
| 缓存 | GET 响应可缓存，除非缓存控制指示不允许 | POST 只有在显式满足可缓存条件时才能缓存，而大多数缓存实现主要支持 GET/HEAD |
| 参数/内容 | 实际 Web 应用常用 query 表达筛选、排序、分页；GET 请求内容没有通用语义，不应在没有与服务端明确约定时发送 | 内容通常放 request body，可用 JSON、表单、multipart 等媒体类型 |
| URL 和可分享性 | query 是目标 URI 的一部分，适合可复制、收藏、历史记录的查询状态 | body 不是 URL 的一部分，普通收藏不会保留请求体 |
| 安全性 | 敏感 query 可能进入历史、服务器/代理日志和分析系统，不适合传密码 | POST body 不会让请求天然安全；无论 GET 还是 POST，都必须使用 HTTPS、做身份验证与输入校验 |

HTTP 规范定义 GET 为 safe 且 idempotent；POST 本身不是 safe/idempotent。安全/幂等说的是“用户请求的预期语义”，并不阻止服务器记日志等附带效果。来源：[RFC 9110 方法属性](https://httpwg.org/specs/rfc9110.html#method.properties)、[GET](https://httpwg.org/specs/rfc9110.html#GET)、[POST](https://httpwg.org/specs/rfc9110.html#POST)。

### Axios 中的对应写法

- GET 查询参数用 `params`：`request.get('/cities/events', { params })`，Axios 会将其序列化为 URL query。
- POST 内容用 `data`：`request.post('/auth/login', data)`，Axios 会将其作为请求体。

Axios 官方将 `params` 定义为 URL parameters，将 `data` 定义为 request body。来源：[Axios Request Config](https://axios-http.com/docs/req_config)。项目代码：[`cities.ts`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/api/cities.ts:16)、[`auth.ts`](/Users/aaron/LoveCoding/21_React/高阶/data-pilot/src/api/auth.ts:4)。

### 面试可直接说

> GET 和 POST 最核心的区别是 HTTP 语义。GET 用来获取资源，属于安全、幂等方法，响应也更适合缓存；POST 是让目标资源处理提交内容，默认不幂等，所以下单等场景重试时需要幂等键。参数位置是常见差异但不是全部：在 Axios 中 GET 通常用 `params` 放 query，POST 用 `data` 放 body。POST 不会因为参数在 body 就自动安全，两者都需要 HTTPS、鉴权和输入校验。云枢智慧城市数据平台中获取验证码用 GET，登录提交用户名、密码和验证码用 POST，就是按照这种语义区分的。

两个常见追问可以继续这样答：

- **GET 有固定长度限制，POST 没有吗？** HTTP 规范没有给出所有实现共用的“GET 最大长度”，而是建议发送方和接收方至少支持 8000 octets 的 URI；实际上还会受浏览器、网关、Web 服务器和应用配置限制。POST body 也不是无限大，同样受各层限制。来源：[RFC 9110 第 4.1 节](https://httpwg.org/specs/rfc9110.html#uri.references)。
- **GET 是 safe，是不是就绝对没有副作用？** safe 指客户端请求的语义是只读；服务器仍然可以记录日志、统计访问。但业务不应把删除、扣款等操作设计成 GET，否则预取、爬虫或重试都可能产生意外后果。来源：[RFC 9110 安全方法](https://httpwg.org/specs/rfc9110.html#safe.methods)。

## 可以追加到项目总结中的“边界与反思”

这部分不是必须背诵，但能避免把尚未完成的功能说成已完成：

1. **开发代理与生产部署分开**：Vite `server.proxy` 只是开发服务器方案，上线要额外解决 API 地址和跨域。
2. **认证与授权分开**：JWT/token 证明登录态，RBAC 判断已登录用户能做什么；前端菜单过滤只是体验层，后端接口授权才是安全边界。
3. **路由判过期不等于无感刷新**：真正的刷新还需要 refresh token 协议、请求去重/排队、刷新失败退出和重放的幂等边界。
4. **公共请求层要与特殊传输分开**：普通 JSON API 可走 Axios 实例；AI 的流式响应如果使用 Fetch/ReadableStream，需要单独复用 token 、超时、取消和错误规则，否则会形成两套不一致的网络层。

Bearer token 由任何持有者即可使用，因此规范要求它在存储和传输中受保护，并在 HTTP 中优先使用 `Authorization: Bearer <token>` 方式传输。来源：[RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750)。
